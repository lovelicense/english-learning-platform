# 안드로이드 모바일 앱 전환 계획

## 목표
- 현재 웹/백엔드 구조를 최대한 재사용하면서 안드로이드 앱을 추가한다.
- 가장 중요한 모바일 기능은 장시간 녹음, 안정적 업로드, STT 결과 확인, 영어 표현 학습 흐름 연결이다.
- 첫 릴리스에서는 "모바일에서 녹음 -> 업로드 -> STT 확인 -> 문장 수정 -> 표현 생성 -> TTS 재생"까지를 우선 완성한다.


## 추천 기술 선택
추천:
- React Native + Expo + TypeScript

이유:
- 현재 웹이 Next.js/TypeScript 기반이라 개발 언어와 사고방식을 맞추기 쉽다.
- 공용 타입, API 클라이언트, 일부 비즈니스 로직을 재사용하기 좋다.
- 초기 안드로이드 MVP를 빠르게 만들기 좋다.
- 나중에 iOS까지 확장할 때도 유리하다.

비추천 우선순위:
- Flutter

Flutter도 장점은 있지만, 현재 JS/TS 기반 자산을 재사용하기 어렵고 초기 전환 비용이 더 크다.


## 권장 아키텍처
현재:
- `apps/web`: Next.js
- `apps/api`: NestJS
- `apps/worker`: 비동기 처리
- `packages/*`: 공용 패키지

추가:
- `apps/mobile`: Expo React Native 앱

모바일 앱은 기존 API를 그대로 사용한다.

핵심 원칙:
- 녹음/STT/TTS 처리 로직은 서버 중심 유지
- 모바일은 녹음, 임시 저장, 업로드, 상태 조회, 학습 UI에 집중
- 공용 타입/DTO는 가능한 한 `packages/shared` 또는 별도 공용 패키지로 정리


## 모바일에서 특히 먼저 고려할 것
웹보다 모바일에서 더 중요한 항목:
- 장시간 녹음 안정성
- 앱 백그라운드 전환 시 동작
- 네트워크 불안정 시 업로드 재시도
- 업로드 중 앱 종료/복귀 처리
- 로컬 파일 임시 저장
- 분할 업로드
- 배터리/네트워크 사용량
- JWT 안전 저장
- 권한 처리
  - 마이크 권한
  - 저장소 접근


## 모바일 MVP 범위
1차 MVP:
- 로그인
- 녹음 시작/중지
- 녹음 파일 로컬 저장
- 녹음 세션 생성
- 파트 업로드
- 업로드 상태 표시
- STT 결과 조회
- 문장 수정/삭제
- 내 화자 선택
- 영어 표현 생성
- TTS 재생

2차 확장:
- 말하기 테스트
- 오늘의 복습
- TTS 완료 표현 모아보기
- 오프라인 임시 저장
- 백그라운드 업로드 개선
- 푸시/로컬 알림


## 추천 화면 구조
탭 기준:
- 홈
- 녹음
- 표현
- 복습
- 설정

상세 화면:
- 로그인 화면
- 새 녹음 화면
- 업로드/처리 상태 화면
- 녹음 상세 화면
- 표현 상세 화면

가장 중요한 전용 화면:

  - 경과 시간
  - 녹음 중 상태
  - 분할 업로드 상태
  - 취소/중지 버튼


## 녹음/업로드 구조 권장안
모바일에서는 웹보다 아래 구조가 더 안전하다.

권장 흐름:
1. 앱에서 녹음 시작
2. 일정 길이 단위로 로컬 파일 저장
3. `recording-session` 생성
4. 파트별 presign 발급
5. 파트 업로드
6. 파트 complete 호출
7. 전체 finalize
8. worker가 STT 처리
9. 앱은 polling 또는 새로고침으로 상태 확인

권장 파트 길이:
- 3분 ~ 10분

이유:
- 너무 짧으면 업로드 횟수가 많아짐
- 너무 길면 실패 복구 비용이 커짐

1차 MVP 권장:
- 5분 단위 파트 업로드

## 인증/저장 전략
권장:
- 로그인 후 JWT를 Secure Storage에 저장

예시:
- Expo Secure Store

로컬 상태:
- 현재 업로드 중 세션
- 로컬 파일 경로
- 업로드 완료 여부
- 실패 파트 목록

이 정보는 앱 재실행 후 복구 가능해야 한다.


## API 준비 체크리스트
모바일 개발 전에 확인하면 좋은 것:
- 로그인/토큰 갱신 정책
- `recording-session` 흐름의 안정성
- 파트별 업로드 재시도 가능 여부
- 세션 상태 조회 API
- 세션 실패 사유 노출
- 녹음/문장/표현/TTS 조회 API 응답 일관성
- 모바일에서 필요한 최소 목록 조회 API

추가로 고려할 API:
- 업로드 재개용 세션 조회
- 실패 파트 재시도 전용 엔드포인트
- 최근 녹음 이어하기 API


## 안드로이드 MVP 개발 순서

- 실패 시 재시도

### 6단계

- TTS 재생

- 오늘의 복습


## Expo 기준 라이브러리 후보
권장 후보:
- 라우팅: Expo Router
- 서버 상태 관리: TanStack Query
- 전역 상태: Zustand
- 인증 저장: expo-secure-store
- 오디오 녹음/재생: expo-av 또는 expo-audio 계열 검토
- 파일 접근: expo-file-system

주의:
- 장시간 녹음과 백그라운드 제약은 Expo 관리형에서 제한이 있을 수 있다.
- 필요시 특정 기능만 prebuild 또는 native module 검토


## 리스크
### 1. 장시간 녹음 안정성
- 가장 큰 리스크
- 앱 백그라운드, 화면 꺼짐, 통화, 절전모드 영향 가능

대응:
- 짧은 파트 단위 저장
- 업로드 재개 전략
- 실기기 테스트 우선

### 2. 브라우저와 다른 오디오 포맷
- 안드로이드는 기기별 녹음 포맷 차이 가능

대응:
- 서버가 처리 가능한 포맷 기준 확정
- 필요시 업로드 전 포맷 정규화

### 3. 네트워크 불안정
- 긴 녹음 업로드 실패 가능성 높음

대응:
- multipart/part 업로드
- 실패 파트만 재업로드

## 결론
현재 프로젝트는 모바일 확장에 유리한 상태다.

이유:
- API/Worker 중심 구조가 이미 있음
- 녹음 세션/비동기 처리 개념이 있음
- 모바일에서 중요한 "긴 녹음 -> 나눠 업로드 -> 나중에 이어서 처리" 구조와 잘 맞음

추천 방향:
- 안드로이드는 `React Native + Expo`
- `apps/mobile` 추가
- 1차는 녹음/업로드/STT 결과 확인 중심 MVP
- 이후 표현/TTS/테스트/복습 확장
